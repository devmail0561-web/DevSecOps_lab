1. Introduction

1.1 Contexte

Une organisation prévoit de mettre en production une application web permettant à ses utilisateurs de créer un compte, de s'authentifier et d'accéder à des ressources contenant des données sensibles. Avant le déploiement, l'équipe sécurité mandate un audit complet afin d'identifier les vulnérabilités susceptibles de compromettre la protection des données.

Cette évaluation est conduite dans le rôle de Cybersecurity Analyst / Junior DevSecOps Engineer.

6. Remédiations

6.1 V2 — SQL Injection (CWE-89) — Requêtes paramétrées

Cause racine : Interpolation directe de email dans la requête SQL via template literal. Le payload ' OR '1'='1'-- ferme la chaîne, ajoute une condition vraie et commente le reste.

// VULNÉRABLE
db.query(`SELECT * FROM Users WHERE email = '${email}' AND deletedAt IS NULL`)

// CORRIGÉ — Sequelize parameterized query (remediation/sqli_fix.js)
const user = await models.User.findOne({
  where: { email: email, deletedAt: null }
})

Justification : Les requêtes paramétrées séparent structurellement le code SQL des données. La valeur email est transmise comme paramètre lié, jamais interprétée comme SQL. Recommandé par OWASP ASVS v4.0 section 5.3.4.

Vérification : Relancer test_auth.sh → payload SQLi doit retourner HTTP 401 au lieu de HTTP 200.

6.2 V3 — IDOR (CWE-639) — Middleware d'autorisation

Cause racine : Le middleware d'authentification vérifie la validité du JWT mais ne compare pas l'ID du panier dans l'URL avec celui encodé dans le JWT (bid).

// CORRIGÉ (remediation/idor_fix.js)
function verifyBasketOwnership(req, res, next) {
  const requestedId = parseInt(req.params.id, 10)
  if (!req.user || req.user.data.bid !== requestedId) {
    return res.status(403).json({ error: 'Forbidden',
      message: 'You can only access your own basket.' })
  }
  next()
}
// router.get('/:id', security.isAuthorized, verifyBasketOwnership, basketHandler)

Justification : Le JWT contient déjà l'ID du panier (bid), donc aucune requête DB supplémentaire n'est nécessaire. La vérification est O(1) en temps de calcul.

Vérification : Relancer EXP-02 → GET /rest/basket/1 avec JWT attaquant doit retourner HTTP 403.

6.3 V7 — Mass Assignment (CWE-915) — Whitelist de champs

Cause racine : Le handler PUT /api/Users/:id passe req.body directement à User.update() sans filtrer les champs sensibles.

// VULNÉRABLE
await models.User.update(req.body, { where: { id: req.params.id } })

// CORRIGÉ (remediation/mass_assignment_fix.js)
const ALLOWED_FIELDS = ['username','password','email',
                        'securityQuestion','securityAnswer','profileImage']
const safeUpdates = _.pick(req.body, ALLOWED_FIELDS)
// 'role' absent de la whitelist → ignoré silencieusement
await models.User.update(safeUpdates, { where: { id: userId } })

Justification : L'approche whitelist protège automatiquement contre les futurs champs sensibles ajoutés au modèle. _.pick est déjà une dépendance de Juice Shop (lodash) — aucun package supplémentaire.

Vérification : Relancer EXP-05 → HTTP 200 mais role inchangé en base de données.

6.4 V1 — En-têtes manquants (CWE-16) — helmet.js + Nginx

Cause racine : Juice Shop n'intègre pas de middleware helmet ni de reverse proxy configuré pour les headers de sécurité.

// CORRIGÉ (security-config/helmet_config.js)
app.use(helmet({
  contentSecurityPolicy: { directives: { defaultSrc: ["'self'"], ... } },
  hsts: { maxAge: 31536000, includeSubDomains: true, preload: true },
  referrerPolicy: { policy: 'strict-origin-when-cross-origin' }
}))

Vérification : curl -I http://localhost:3000 | grep -E 'Strict-Transport|Content-Security|Referrer' → les 3 headers présents.

7. Pipeline de sécurité

7.1 Architecture des 6 étapes Jenkins

1. Checkout — récupération du code (commit, branche)
↓
2. Build / Preparation — démarrage de l'environnement, vérification disponibilité Juice Shop
↓
3. Security Analysis — SAST (Semgrep) + SCA (npm audit)
↓
4. Additional Security Check — DAST (OWASP ZAP) + Secret Detection (trufflehog)
↓
5. Report Generation — consolidation de tous les résultats
↓
6. Notification — email HTML via MailHog (emailext)

Chaque étape utilise catchError(buildResult: 'UNSTABLE', stageResult: 'FAILURE') : une vulnérabilité détectée marque l'étape en échec mais le pipeline continue pour collecter tous les résultats.

9. Décision de déploiement

🔴 REJECT DEPLOYMENT

L'application n'est pas prête à être déployée en production.

Deux vulnérabilités de sévérité Critical non corrigées rendent tout déploiement inacceptable :

  1. SQL Injection (CVSS 9.8) — Exploitation confirmée : JWT administrateur obtenu sans aucun identifiant valide. Compromet la confidentialité et l'intégrité de toutes les données de l'application.
  2. Mass Assignment (CVSS 8.8) — Exploitation confirmée : élévation de privilège auto-administrée. Tout utilisateur peut devenir administrateur sans autorisation préalable.

De plus, 5 vulnérabilités High (IDOR, Data Exposure, Path Traversal, Rate Limiting, XSS) augmentent significativement la surface d'attaque.

Conditions pour Accept with Conditions : Correction et re-test de V2 + V7 (bloquants absolus), plan documenté pour V3, V4, V5, V6, V9, re-exécution du pipeline avec zéro Critical.

10. Conclusion et analyse critique

10.1 Synthèse

Cette évaluation a identifié 9 vulnérabilités couvrant 6 des 10 catégories du Top 10 OWASP 2021. Les vulnérabilités les plus critiques — l'injection SQL (CVSS 9.8) et le Mass Assignment (CVSS 8.8) — permettent respectivement d'obtenir un accès administrateur complet sans aucun identifiant, et de créer des comptes avec des privilèges élevés.

La chaîne d'exploitation démontrée (SQLi → JWT admin → exfiltration de données → IDOR) illustre pourquoi une seule vulnérabilité critique peut suffire à compromettre la totalité d'un système. Les remédiations implémentées (requêtes paramétrées, middleware d'autorisation, whitelist de champs) sont alignées avec les recommandations de l'OWASP ASVS v4.0. Le pipeline Jenkins automatise 4 types de contrôles de sécurité et notifie l'équipe à chaque commit.

10.2 Analyse critique — Un outil de sécurité sans alerte garantit-il la sécurité ?

Non — de façon catégorique. Plusieurs limites structurelles rendent cette garantie impossible.

Les faux négatifs sont inévitables. Chaque outil a un périmètre technique délimité. Dans cette évaluation, la vulnérabilité V7 (Mass Assignment, CVSS 8.8) n'est détectée ni par Semgrep ni par OWASP ZAP, car elle nécessite une compréhension du modèle de données applicatif — seul un test manuel ciblé peut la trouver. ZAP a scanné l'intégralité de l'application sans la détecter. Un résultat « aucune alerte » de ZAP n'aurait donc pas garanti l'absence de cette vulnérabilité critique.

La couverture des règles est structurellement incomplète. Les outils SAST travaillent avec des règles qui ne couvrent pas tous les vecteurs possibles. Un pattern d'injection non documenté, une logique métier particulière, ou une vulnérabilité émergeant de l'interaction entre plusieurs composants peuvent traverser tous les filtres existants sans déclencher d'alerte.

Les faux positifs créent la fatigue d'alerte. À l'inverse, un outil générant trop de faux positifs conduit les équipes à ignorer les alertes par lassitude. Si 45 des 50 alertes Semgrep sont des faux positifs, le risque est réel que les 5 vraies vulnérabilités soient négligées lors de la revue. La qualité des règles et leur pertinence pour le contexte applicatif est aussi importante que leur quantité.

L'analyse humaine est irremplaçable. Un attaquant réel raisonne par objectif (obtenir des données administrateurs, contourner un paiement) et explore des chemins que les outils automatiques ne parcourent pas. L'enchaînement logique de plusieurs vulnérabilités mineures en une chaîne d'exploitation majeure — comme démontré ici — nécessite un raisonnement contextualisé que les outils actuels ne peuvent pas reproduire.

Conclusion : Un pipeline de sécurité automatisé constitue une couche de défense robuste et indispensable. Il garantit une vérification systématique à chaque commit, réduit la surface d'exposition et accélère la détection des vulnérabilités les plus courantes. Mais il doit être complété par des revues de code humaines, des tests d'intrusion périodiques, et une culture de sécurité chez les développeurs. La sécurité est un processus continu, pas un état atteignable par un unique scan automatique.
