1Introduction

Contexte

Une organisation prévoit de mettre en production une application web permettant à ses utilisateurs de créer un compte, de s'authentifier et d'accéder à des ressources contenant des données sensibles. Avant le déploiement, l'équipe sécurité mandate un audit complet afin d'identifier les vulnérabilités susceptibles de compromettre la protection des données.

Cette évaluation est conduite dans le rôle de Cybersecurity Analyst / Junior DevSecOps Engineer.

V2 — SQL Injection

Critical CWE-89 CVSS 9.8

Le formulaire de connexion (POST /rest/user/login) est vulnérable à une injection SQL classique. L'entrée email est interpolée directement dans la requête SQL sans nettoyage.

Preuve d'exploitation — EXP-01 (14/08/2026)
POST /rest/user/login
{"email":"' OR '1'='1'--","password":"x"}

→ HTTP 200 — JWT administrateur retourné
  eyJ0eXAiOiJKV1QiLCJhbGciOiJSUzI1NiJ9.eyJkYXRhIjp7ImlkIjoxLCJ...
JWT décodé
{ "data": { "id": 1, "email": "admin@juice-sh.op", "role": "admin",
           "password": "0192023a7bbd73250516f069df18b500" }, "bid": 1 }

Le hash MD5 0192023a7bbd73250516f069df18b500 correspond à admin123 — le mot de passe admin est exposé dans chaque token JWT.

V3 — IDOR — Accès non autorisé aux paniers

High CWE-639 CVSS 8.1

Le middleware d'authentification vérifie la validité du JWT mais ne contrôle pas que l'utilisateur est propriétaire du panier demandé (/rest/basket/:id).

Preuve d'exploitation — EXP-02 (10/08/2026)
Compte attaquant : attacker_7417@lab.local
GET /rest/basket/1  [JWT attaquant]  →  HTTP 200

Contenu panier victime :
  Apple Juice (1000ml)   × 2  — 1.99 €
  Orange Juice (1000ml)  × 3  — 2.99 €
  Eggfruit Juice (500ml) × 1  — 8.99 €

V4 — Path Traversal + Null Byte Bypass

High CWE-22/626 CVSS 7.5

Le répertoire /ftp/ est accessible sans authentification. Un filtre d'extension bloque les fichiers .bak, mais le double encodage %2500 (null byte) contourne ce filtre.

Preuves — EXP-03
GET /ftp/acquisitions.md              →  HTTP 200  ✓ Document interne téléchargé
GET /ftp/legal.md                     →  HTTP 200  ✓ Document juridique téléchargé
GET /ftp/package.json.bak             →  HTTP 403  ✗ Filtré
GET /ftp/package.json.bak%2500.md     →  HTTP 200  ✓ Filtre contourné (null byte)

V7 — Mass Assignment — Escalade de privilège

Critical CWE-915 CVSS 8.8

L'API PUT /api/Users/:id passe req.body directement à User.update() sans filtrer les champs. N'importe quel utilisateur peut modifier son propre champ role.

Preuve — EXP-05
PUT /api/Users/6
Authorization: Bearer <JWT_ATTAQUANT>
{"role":"admin"}

→ HTTP 200 — champ role modifié en base de données

6Remédiations

V2 — SQL Injection (CWE-89)

Critical · CVSS 9.8
Cause racine

Le handler de login construit sa requête SQL par interpolation directe de la valeur email via un template literal. Le payload ' OR '1'='1'-- ferme la chaîne, ajoute une condition toujours vraie et commente le reste.

Remédiation — Fichier : remediation/sqli_fix.js
// VULNÉRABLE
db.sequelize.query(`SELECT * FROM Users WHERE email = '${req.body.email}'...`)

// CORRIGÉ — Sequelize génère WHERE email = ? (paramètre lié par le driver)
const user = await models.User.findOne({ where: { email: email, deletedAt: null } })
Justification

Les requêtes paramétrées séparent structurellement le code SQL des données. La valeur email est transmise comme paramètre lié — jamais interprétée comme SQL. Recommandé par OWASP ASVS v4.0 §5.3.4.

Vérification
JUICE_SHOP_URL=http://localhost:3000 bash scripts/test_auth.sh
# Attendu : HTTP 401 sur payload SQLi — "[OK] SQLi rejetée"

V3 — IDOR (CWE-639)

High · CVSS 8.1
Cause racine

Le middleware d'authentification vérifie la validité du JWT mais ne compare pas l'ID du panier dans l'URL (req.params.id) avec celui encodé dans le JWT (req.user.data.bid).

Remédiation — Fichier : remediation/idor_fix.js
function verifyBasketOwnership(req, res, next) {
  const requestedId = parseInt(req.params.id, 10)
  if (!req.user || req.user.data.bid !== requestedId) {
    return res.status(403).json({ error: 'Forbidden: not your basket.' })
  }
  next()
}
// router.get('/:id', security.isAuthorized, verifyBasketOwnership, handler)
Justification

Le JWT contient déjà le bid (basket ID) de l'utilisateur — la vérification est O(1), sans requête DB supplémentaire. Le JWT étant signé RS256, un attaquant ne peut pas modifier le champ bid sans invalider la signature.

Vérification
bash scripts/test_exploitation.sh
# EXP-02 : GET /rest/basket/1 avec JWT attaquant → HTTP 403 attendu

V7 — Mass Assignment (CWE-915)

Critical · CVSS 8.8
Cause racine

Le handler PUT /api/Users/:id passe req.body directement à User.update(). N'importe quel champ du modèle (role, isActive, totpSecret...) peut être modifié.

Remédiation — Fichier : remediation/mass_assignment_fix.js
const ALLOWED_FIELDS = ['username','password','email',
                        'securityQuestion','securityAnswer','profileImage']
// 'role' absent → ignoré silencieusement
const safeUpdates = _.pick(req.body, ALLOWED_FIELDS)
await models.User.update(safeUpdates, { where: { id: userId } })
Justification

L'approche whitelist protège automatiquement contre les futurs champs sensibles. _.pick est déjà une dépendance de Juice Shop (lodash) — aucune dépendance supplémentaire.

Vérification
curl -X PUT -H "Authorization: Bearer $JWT" \
  -d '{"role":"admin"}' http://localhost:3000/api/Users/$ID
# Attendu : HTTP 200 MAIS role inchangé en DB

9Décision de déploiement

Décision de déploiement
Reject Deployment

Deux vulnérabilités de sévérité Critical non corrigées rendent tout déploiement inacceptable :

V2 — SQL Injection (CVSS 9.8) : exploitation confirmée — JWT administrateur obtenu sans aucun identifiant valide. Compromet la confidentialité et l'intégrité de toutes les données.

V7 — Mass Assignment (CVSS 8.8) : tout utilisateur peut s'auto-attribuer le rôle admin via un simple PUT avec {"role":"admin"}.

Conditions pour Accept with Conditions

  • Correction et re-test de V2 (SQLi) et V7 (Mass Assignment) — bloquants absolus
  • Plan documenté et daté pour V3, V4, V5, V6, V9
  • Re-exécution du pipeline : zéro Critical en résultat
  • Monitoring de sécurité en place avant ouverture au public

10Conclusion et analyse critique

Synthèse

Cette évaluation a identifié 9 vulnérabilités couvrant 6 des 10 catégories du Top 10 OWASP 2021. La chaîne d'exploitation démontrée — SQLi → JWT admin → exfiltration de données → IDOR — illustre comment une seule vulnérabilité critique peut suffire à compromettre l'intégralité d'un système. Les remédiations implémentées (requêtes paramétrées, middleware d'autorisation, whitelist de champs) sont alignées avec l'OWASP ASVS v4.0. Le pipeline Jenkins automatise 4 types de contrôles et notifie l'équipe à chaque commit.

Un outil sans alerte garantit-il qu'une application est sécurisée ?

Réponse : Non — de façon catégorique. Plusieurs limites structurelles rendent cette garantie impossible.

Les faux négatifs sont inévitables. Dans cette évaluation, la vulnérabilité V7 (Mass Assignment, CVSS 8.8) n'a été détectée ni par Semgrep ni par OWASP ZAP — elle nécessite une compréhension du modèle de données applicatif. ZAP a scanné l'intégralité de l'application sans la détecter. Un résultat « aucune alerte » de ZAP n'aurait donc pas garanti l'absence de cette vulnérabilité critique.

La couverture des règles est structurellement incomplète. Les outils SAST travaillent avec des règles qui ne couvrent pas tous les vecteurs possibles. Une logique métier particulière, ou une vulnérabilité émergeant de l'interaction entre plusieurs composants, peut traverser tous les filtres existants.

Les faux positifs créent la fatigue d'alerte. Si 45 des 50 alertes Semgrep sont de faux positifs, le risque est réel que les 5 vraies vulnérabilités soient négligées lors de la revue.

L'analyse humaine est irremplaçable. L'enchaînement logique de plusieurs vulnérabilités mineures en une chaîne d'exploitation majeure — comme démontré ici — nécessite un raisonnement contextualisé que les outils actuels ne peuvent pas reproduire.

Conclusion Un pipeline DevSecOps constitue une couche de défense robuste et indispensable. Il garantit une vérification systématique à chaque commit. Mais il doit être complété par des revues de code humaines, des tests d'intrusion périodiques, et une culture de sécurité chez les développeurs. La sécurité est un processus continu, pas un état atteignable par un unique scan automatique.
